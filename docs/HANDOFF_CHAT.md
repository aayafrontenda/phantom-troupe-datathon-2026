## 2. Кейс (ТЗ Datathon 26, ForteBank) — главное

- Сервис с веб-интерфейсом и API: загрузка `.mov` → вердикт «Нарушение не обнаружено» / «Обнаружены признаки возможных
  нарушений» → для каждого нарушения тип, таймкод, описание (что видно и почему это может быть нарушением),
  1–3 кадра-доказательства, норма (документ + пункт).
- API: `POST /api/v1/analyze` (поле `file`) → `job_id`; `GET /api/v1/jobs/{job_id}` → `processing|done|failed`, `verdict`
  (`violation|no_violation`), `violations[]` с `type`, `timecode_sec`, `description`, `evidence_frames[{timestamp_sec, image_base64}]`.
  Ключ в `X-API-Key`, без него — отказ. Жюри оценивает **автоматически** по этой схеме.
- Лимит: 5 минут на видео (иначе «необработано»). Финальная проверка — 5+ видео; финальное видео снято **под другим углом**.
- Только локальные модели, без облачных AI-API; после загрузки весов — без интернета. Лицензии — с коммерческим использованием.
- Нельзя утверждать то, что не видно (проводки, сверки). Результат — подсказка проверяющему.
- Тестовые видео нельзя использовать для обучения, публиковать, передавать.
- Критерии (100): обнаружение 25 (по вердикту на видео), локализация 15 (таймкод и кадр), классификация 15,
  обоснованность правил 15 (без выдуманных ссылок), устойчивость 10 (новые видео и ракурс), готовность продукта 10,
  техническое решение 10 (включая локальность).
- FAQ: закрытого списка типов нет; в тесте могут быть новые типы; ложных срабатываний — как можно меньше,
  **пропуск недопустим**; нарушения «по бездействию» — таймкод на усмотрение команды; свои съёмки разрешены;
  интерфейс на любом языке; авторизация/история/пакетная загрузка не нужны; звук не использовать;
  финалисты питчат 5 мин + 2 мин вопросы; равенство баллов решает питч.

## 5. Архитектурные решения

- Гибрид: детектор RT-DETR r18 (Apache-2.0) на каждом кадре (2 fps) → сигналы состояния → кандидаты событий → локальная
  VLM Qwen2.5-VL-7B (Apache-2.0, 4 бит через Ollama, ~6 ГБ) проверяет только окна вокруг кандидатов (≤ 12 вызовов)
  → правила из `rules_kb.yaml` → JSON по ТЗ. Без VLM работают правила только по детектору.
- Нельзя: Ultralytics YOLO (AGPL-3.0), Qwen2.5-VL-3B (исследовательская лицензия).
- RTX 4070 Laptop — 8 ГБ VRAM: только 4-битная 7B-модель; цель ≤ 60 с на видео, потому что жюри может прислать 5 видео
  сразу, а GPU одна (очередь, лимит 280 с от загрузки — пайплайн сам сокращает проверки).
- Сервер — ROG; публичный адрес — Cloudflare Tunnel (`cloudflared tunnel --url http://localhost:8000`); ноутбук не спит.
- Описания — только наблюдаемое («на видео не зафиксировано…»), норма дублируется в конце `description`
  (автооценка видит только поля схемы).
- Уникальные функции: live-режим с камеры (детектор + правила, алерты), дорожки состояний под плеером,
  «Подтвердить / Ложное» (обратная связь), печать акта.

## 8. Следующие шаги (ML) — по убыванию отдачи

1. Окружение на ROG и первый запуск модели (`docs/tasks/ML.md`, разделы 0–1).
2. Базовая оценка: `python -m ml.eval.evaluate --videos data\open\videos`, разбор FN/FP по `meta.scenes`.
3. Проход по визитам (несколько человек у стола) — один вызов VLM на визит с 6–8 кадрами и вопросами для T06/T07/T09/T10.
4. Сигнал «кассир ушёл» + вопросы VLM про экран / деньги на столе / сейф (T01–T03); калибровка `SCREEN_ON_V` на Х-22/23/28/29.
5. Дверь после входа/выхода (T04) по парам Х-31 / Х-32, Х-33.
6. Таймкоды из сигналов, а не из VLM, если она ошибается во времени; цель — медиана ≤ 2 с.
7. Пороги: 0 пропусков на обучающих, потом минимум ложных на 20 нормальных.
8. Скорость ≤ 60 с на Х-14; проверка 5 видео одновременно.
9. Свои ролики под новым углом; проверка по ракурсам A–E.
