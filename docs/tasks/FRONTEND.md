# Frontend + сдача — инструкция

**Кто:** MacBook Air M1.
**Отвечаешь за:** `frontend/` — интерфейс проверяющего и live-страница; `docs/` — пакет сдачи (раздел 8 ТЗ) и слайды.

Контекст — `AGENTS.md`, данные — `docs/api_contract.md` и `examples/sample_response.json`.
Резервный интерфейс уже работает (`backend/static/index.html`) — используй его как рабочий образец логики,
твоя задача — сделать красивую и удобную версию.

## 0. Подготовка

1. Backend в mock-режиме у себя (нужен Python 3.11+):
   ```bash
   python3 -m venv .venv && source .venv/bin/activate
   pip install -r requirements.txt && cp .env.example .env
   ./deploy/run_server.sh                     # http://127.0.0.1:8000, ANALYZER=mock
   ```
2. Node 20+ и приложение:
   ```bash
   cd frontend
   npm create vite@latest . -- --template react-ts     # «Ignore files and continue»
   npm install
   npm install tailwindcss @tailwindcss/vite
   ```
   В `vite.config.ts`: плагин `tailwindcss()` и прокси на backend:
   ```ts
   server: { proxy: { '/ui': { target: 'http://127.0.0.1:8000', changeOrigin: true, ws: true } } }
   ```
   В `src/index.css`: `@import "tailwindcss";`. Запуск: `npm run dev`.

## 1. Данные

- Загрузка: `POST /ui/api/analyze` (FormData, поле `file`) → `{job_id}`.
- Статус: `GET /ui/api/jobs/{id}` раз в секунду → `status`, `stage`, `progress`, `queue_position`;
  при `done` — `verdict`, `violations[]`, `timeline`, `meta`, `processing_sec`.
- Справка по типам и нормам: `GET /ui/api/info`.
- Обратная связь: `POST /ui/api/jobs/{id}/feedback` `{violation_index, decision: "confirm"|"reject"}`.
- Live: WebSocket `/ui/api/live` (протокол в `docs/api_contract.md`).

Видео для плеера — локальный `URL.createObjectURL(file)`, на сервер повторно не ходим.

## 2. Обязательный сценарий (раздел 4 ТЗ — без него нет баллов за продукт)

1. **Загрузка** — перетаскивание или выбор `.mov`, проверка расширения, понятные ошибки (400/413/сеть).
2. **Статус обработки** — этапы `queued → frames → detection → vlm → report`, прогресс, секунды, место в очереди.
3. **Вердикт** — крупно и дословно: «Нарушение не обнаружено» / «Обнаружены признаки возможных нарушений».
4. **Карточка нарушения** — тип, таймкод `мм:сс.с`, описание (что видно и почему может быть нарушением).
5. **Кадры-доказательства** — 1–3 кадра (`data:image/jpeg;base64,…`), клик — увеличение и перемотка видео.
6. **Норма** — документ + пункт + цитата + ссылка на adilet (`rule.refs`), метка вида: прямая норма / косвенная / внутренний регламент
   (`rule.kind`), оговорка `rule.caveat`.
7. **Плеер** с метками нарушений на шкале; клик по карточке или метке — перемотка на 1 с раньше события.
8. Подпись: «Результат — подсказка для проверки человеком, а не окончательное заключение» (раздел 7 ТЗ).

## 3. Уникальные функции (после обязательного)

1. **Дорожки состояний** под плеером из `timeline`: людей в кадре, экран включён, телефон, еда/напиток, сумка —
   синхронно с плеером. Показывает, *почему* сработало правило.
2. **Live-страница**: камера ноутбука → WebSocket → рамки поверх видео и лента алертов с нормами.
   Логика уже есть в `backend/static/live.html` — перенеси в React и сделай красиво.
3. **«Подтвердить / Ложное срабатывание»** у каждой карточки → feedback.
4. **Печать акта проверки**: `window.print()` + стили `@media print` (вердикт, нарушения, кадры, нормы) — PDF без библиотек.
5. Тёмная тема, нормальный вид на телефоне (жюри может открыть с телефона).

Не нужно (FAQ 27): авторизация, история проверок, пакетная загрузка.

## 4. Сборка

```bash
cd frontend && npm run build        # -> frontend/dist
```
Backend сам отдаёт `frontend/dist` вместо резервного интерфейса. `dist` коммитим в git, чтобы на ROG не ставить Node.

## 6. Питч (5 минут + 2 вопросы, только для финалистов)

1. Проблема: ручной просмотр видео кассы — долго (20 с).
2. Демо: загрузка видео → вердикт → карточка с кадром, таймкодом и нормой (90 с).
3. Live-режим вживую на камере ноутбука (40 с).
4. Как работает: детектор → кандидаты → локальная VLM → правила с нормами; полностью локально, лицензии Apache/MIT (60 с).
5. Качество на обучающих видео и устойчивость к новому ракурсу — цифры от ML (40 с).
6. Развитие: обратная связь проверяющих, RTSP к существующим камерам, новые правила добавляются в YAML (30 с).
