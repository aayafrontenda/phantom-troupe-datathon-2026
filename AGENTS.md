# Контекст проекта для ИИ-помощника и для команды

Читать перед любой правкой. Здесь — что за задача, что нельзя нарушать и как устроен код.

## Задача (Datathon 26, кейс ForteBank)

Локальный AI-сервис: пользователь загружает видео с камеры над кассой (.mov, вид сверху, без звука, 10–145 с, 464×848, 30 fps).
Сервис отвечает:
- вердикт — `violation` («Обнаружены признаки возможных нарушений») или `no_violation` («Нарушение не обнаружено»);
- для каждого нарушения: тип, таймкод, описание (что видно и почему это может быть нарушением), 1–3 кадра-доказательства, норма (документ + пункт).

Жюри прогоняет тестовые видео **через API автоматически**; финальное видео будет **снято под другим углом**.
Подробности ТЗ — `docs/dataset_notes.md` и `docs/api_contract.md`.

## Жёсткие ограничения (нарушение = потеря баллов или дисквалификация)

1. **Только локальные модели.** Никаких облачных AI-API (OpenAI, Gemini, Claude, облачные OCR/VLM) при обработке видео — ни видео, ни кадры, ни их описания не уходят наружу. После скачивания весов сервис работает без интернета (`HF_HUB_OFFLINE=1`).
2. **Лицензии с коммерческим использованием** (FAQ 24): RT-DETR, OWLv2 — Apache-2.0; ByteTrack — MIT; Qwen3.5-4B (используется, `qwen3.5:4b` в Ollama) и Qwen2.5-VL-7B — Apache-2.0. **Нельзя**: Ultralytics YOLO (AGPL-3.0), Qwen2.5-VL-3B (исследовательская лицензия). Новую модель — сначала проверить лицензию на карточке.
3. **Схема ответа API — ровно как в ТЗ** (`ml/schema.py` проверяет). Доп. поля можно, менять обязательные нельзя.
4. **Не больше 5 минут** от загрузки до результата, включая очередь. Цель — ≤ 60 с на видео: жюри может прислать 5 видео одновременно, а GPU одна.
5. **Не утверждать невидимое**: проводки, сверки, документы вне кадра. Формулировки: «на видео не зафиксировано…», «возможное нарушение».
6. **Не выдумывать нормы.** Ссылки на НПА — только из `ml/rules_kb.yaml`. Нет прямой нормы — так и пишем («внутренний регламент банка»).
7. **Тестовые видео жюри** нельзя использовать для обучения и хранить: загрузки через `/api/v1` удаляются через `JURY_VIDEO_TTL_SEC` (1 час). Видео операторов и фрагменты с камер — это данные банка, они хранятся `VIDEO_RETENTION_DAYS` (0 = всегда).

## Как устроен код

```
ml/
  pipeline.py      analyze(path, on_progress, deadline) -> dict   ← главная функция
  video.py         кадры (OpenCV), JPEG/base64
  detector.py      RT-DETR (COCO) через transformers: люди, телефон, напитки, сумки, ноутбук
  signals.py       сигналы состояния по кадрам + кандидаты событий + правила только по детектору
  vlm.py           клиент локальной VLM (Ollama или OpenAI-совместимый vLLM/LM Studio/mlx)
  prompts/checklist_ru.txt   промпт с чек-листом T01–T15
  kb.py, rules_kb.yaml       типы нарушений, описания, нормы
  mock.py          mock-анализатор (тот же формат, без моделей)
  live.py          правила live-режима (поток с камеры)
  schema.py        проверка ответа по ТЗ
  eval/evaluate.py оценка на 42 метках обучающего датасета
  eval/labels_typed.csv  разметка + тип нарушения (T01–T15) + ракурс камеры (A–E)
backend/app/         (подробно — docs/backend.md; контракт — docs/api_contract.md)
  main.py          FastAPI: роутеры, middleware (request-id, метрики), отдача frontend/dist (SPA)
  routers/         jury (/api/v1), auth (вход, пользователи), findings (находки), ui (/ui/api), admin (/admin/api), system
  worker.py        пул воркеров-процессов: приоритет жюри, сторожевой таймер (дедлайн/зависание), ретраи
  jobs.py          жизненный цикл задачи, дедуп по SHA-256, починка результата по схеме, восстановление после рестарта
  findings.py      находки: из результата задачи и из тревог камер (кадры + клип), правка описания, решение оператора,
                   проверка супервайзера, история, фильтры для контроля
  users.py, auth.py  пользователи (operator < supervisor < admin), пароли PBKDF2, cookie-сессии; API-ключи жюри/админа
  analyzers.py     контракт с ML: analyze(path, on_progress, deadline); on_progress.partial(result); warmup()
  db.py, storage.py, events.py, sse.py, metrics.py, reports.py, i18n.py, state.py
  alerts/          policy engine (backend/alerts.yaml), каналы web/telegram/webhook/email
  live/            WebSocket браузера, RTSP/файл-камеры (кольцевой буфер кадров → клип при тревоге), live-анализатор
backend/i18n-kb.json  переводы типов нарушений и норм (en, kk); источник правды по-русски — ml/rules_kb.yaml
backend/templates/ печатный отчёт проверки (ru/kk/en)
frontend/          интерфейс: React + Vite + TS, дизайн forte.kz; роли оператор / супервайзер / админ — docs/tasks/FRONTEND.md
tools/smoke_test.py       проверка «как жюри»: N видео параллельно, время и схема
tools/loadtest.py         нагрузка: параллельные загрузки / шторм live-сессий
tools/simulate_cameras.py камеры-симуляторы из файлов датасета
deploy/                   run_server.sh/.ps1, docker.ps1/.sh, Dockerfile (compose — в корне, см. deploy/DOCKER.md)
```

Пайплайн: кадры 2 fps → детектор → сигналы → кандидаты (вход/выход людей, перемещение, появление
телефона/еды/сумки, экран без присмотра, периодические окна, равномерное покрытие) → VLM проверяет
окно ±3 с вокруг каждого кандидата (≤ `MAX_VLM_CALLS`) → слияние по типу (≤ `MERGE_SEC`) →
порог `MIN_CONFIDENCE` → ответ. Без VLM работают правила только по детектору (`cv_findings`).

## Типы нарушений (из разметки обучающих видео)

| Код | Тип | Обучающие видео |
| --- | --- | --- |
| T01 | Компьютер не заблокирован при уходе | Х-11, Х-22, Х-28 |
| T02 | Наличные/ценности оставлены без присмотра | Х-15, Х-24, Х-26 |
| T03 | Сейф оставлен открытым | Х-20 |
| T04 | Дверь кассы не закрыта | Х-32, Х-33 |
| T05 | Посторонний в кассе | Х-18, Х-30 |
| T06 | Приём наличных без документа | Х-2 |
| T07 | Деньги прошлого клиента на столе при входе следующего | Х-4 (57 с), Х-38 |
| T08 | Работа с деньгами разных клиентов одновременно | Х-47 (= файл Х-4, 68 с) |
| T09 | Клиент ушёл до завершения операции | Х-34 |
| T10 | Возврат клиенту купюры после проверки | Х-1 |
| T11 | Сумка инкассатора без оформления | Х-17 |
| T12 | Ценности в сейф без пересчёта | Х-13 |
| T13 | Личные вещи на рабочем месте | Х-40 |
| T14 | Еда/напитки при работе с наличными | Х-46 |
| T15 | Смартфон в кассе | (нет в данных, вероятен в тесте) |
| T99 | Не установлено | Х-44 |

**Таймкод** — момент, когда нарушение становится видно: кассир встаёт и уходит, входит следующий клиент,
кассир берёт деньги. Так размечены обучающие видео. Для «бездействия» — момент, когда действие должно было произойти.

Нормальные видео — пары к нарушениям: Х-23/Х-29 (заблокировала экран и ушла), Х-16 (инкассатор с документами),
Х-31 (вошла и закрыла дверь), Х-14 (вскрыла сумки и пересчитала), Х-3/Х-19 (клиент сначала даёт удостоверение).


## Пользователи сервиса

- **Оператор** — мониторинг своих камер и лента событий; открывает момент, уточняет описание, решает «нарушение / нет»; загружает видео на проверку.
- **Супервайзер** — раздел «Контроль»: все решения операторов рядом с описанием ИИ и правкой оператора; фильтр «ИИ увидел нарушение, оператор отклонил» (антикоррупционный контроль); отметка «проверено: согласен / не согласен».
- **Администратор** — пользователи, роли, камеры по операторам, состояние сервиса.
Учётные записи: `SEED_USERS` в `.env` при первом запуске, дальше — раздел «Администрирование».
